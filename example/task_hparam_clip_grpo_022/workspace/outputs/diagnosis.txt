## Diagnosis: OOM on 2-GPU GRPO run (returncode 137)

### Root cause
The previous run used ROLLOUT_N=8, which generates 8 responses per prompt. With train_batch_size=8, vLLM must handle 64 concurrent rollout sequences (each up to 2048 tokens). On 2 GPUs sharing FSDP (actor model + optimizer states) and vLLM (KV cache at 0.5 GPU memory utilization), this exhausts GPU memory during initialization — the process was SIGKILL'd before any training step.

### Changes made (5 hollow hyperparameters)
| Parameter | Previous | New | Rationale |
|-----------|----------|-----|-----------|
| CLIP_RATIO | 0.2 | 0.2 | Standard PPO clip; unchanged |
| CLIP_RATIO_C | 3.0 | 3.0 | DAPO dual-clip constant; unchanged |
| NORM_ADV_BY_STD_IN_GRPO | True | True | Standard GRPO advantage normalization; unchanged |
| ROLLOUT_N | 8 | **2** | Drastic memory reduction: 16 sequences instead of 64, ~4× less vLLM KV-cache pressure |
| LOSS_AGG_MODE | token-mean | token-mean | Standard token-level mean; unchanged |

The only change is ROLLOUT_N: 8 → 2. With 2 rollouts per prompt, GRPO still has enough samples for group-relative advantage computation (2 responses per group), while reducing vLLM memory by ~4×. The other four hyperparameters are at well-established DAPO/GRPO defaults and were not the cause of OOM.
