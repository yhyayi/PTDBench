# docker/envs — the conda environment registry

Every non-legacy task names one of these environments in
`metadata.environment.conda`. Each directory is one environment, built by its
own stage in `docker/Dockerfile` at `/opt/conda/envs/<name>` and copied into the
final image **at that same path**.

| file | who writes it | what it is |
|---|---|---|
| `requirements.txt` | generated by `docker/collect_envs.py` | the complete pinned pip closure |
| `conda.yaml` | by hand | interpreter, nvcc, system build libs — nothing else |
| `sources.txt` | by hand | editable source trees a task script names by absolute path |
| `patches/<dir>/*.patch` | by hand | local patches applied to those trees after checkout |
| `build-first.txt` | by hand | names that must land before the `--no-build-isolation` pass |
| `build-flags.txt` | by hand | per-package build env/pip flags (e.g. apex's `--cpp_ext --cuda_ext`) |

`requirements.txt` is *generated and committed*. Each task ships a
byte-identical copy at `environment/requirements.txt`; `collect_envs.py` regroups
them and fails the build if two tasks claiming the same environment disagree.
The union is deliberately not taken — see "Why not merge" below.

## The registry

| env | built from | torch | CUDA | tasks |
|---|---|---|---|---|
| `verl` | `verlai/verl:vllm017.latest` | 2.10.0+cu129 | 12.9 | `verl_hyper/*`, `verl_implementation/*` |
| `slime-rc0` | `slimerl/slime:v0.5.0rc0-cu126` | 2.8.0+cu126 | 12.6 | `rlve_hyper/task_{001,008,012,019}` |
| `slime-v0.3.1` | `slimerl/slime:latest` (slime 0.3.1) | 2.11.0+cu130 | 13.0 | `slime_retool`, `slime_retool_length_hack`, `slime_search_r1`, `slime_search_r1_nomask` |

### Why there are two slime environments

Upstream publishes two slime stacks, and the tasks here are split across both:

| | `slime-rc0` | `slime-v0.3.1` |
|---|---|---|
| image | `slimerl/slime:v0.5.0rc0-cu126` | `slimerl/slime:latest` |
| torch / CUDA | 2.8.0+cu126 / 12.6 | 2.11.0+cu130 / 13.0 |
| sglang | 0.5.0rc0 (git) | 0.5.15.post1 |
| transformers | 4.55 | 5.12.1 |
| megatron-core | `48406695` | `core_v0.16.0` (`3bec9aa9`) |
| flash_attn | 2.7.4.post1 | 2.8.3 |

An earlier revision of this file argued for merging them onto the rc stack. That
was wrong, and the reason is concrete rather than aesthetic: the retool and
search-r1 recipes import sglang's private constants —

```python
# tasks/slime_retool/workspace/slime/ray/rollout.py:15
from sglang.srt.constants import (
    GPU_MEMORY_TYPE_CUDA_GRAPH, GPU_MEMORY_TYPE_KV_CACHE, GPU_MEMORY_TYPE_WEIGHTS,
)
```

`GPU_MEMORY_TYPE_CUDA_GRAPH` does not exist in sglang 0.5.0rc0. The rlve tasks
need only the other two (`tasks/rlve_hyper/*/workspace/train.py:2`), which is
why the rc stack was sufficient for them and is not sufficient here. There is no
sglang version that satisfies both: moving rlve forward would put its four
recorded outcomes on a different torch, and those are exactly the graded
failures this benchmark reproduces (`task_001` grades on held-out reward moving
from -0.611 to -0.639 under `--attention-dropout=0.5`).

So the split is not a fallback — it is the design working as intended. The
environment name is the only identity a task has; two stacks that cannot agree
get two names, and nothing else about the image changes. `docker/smoke.sh`
asserts the asymmetry directly, so a future sglang bump that quietly removes a
constant fails at G2 rather than mid-evaluation.

`slime-v0.3.1` is named for the slime version, not for `latest`: `latest` is a
moving tag and would stop describing the environment the moment upstream
publishes again. 0.3.1 is what the four task workspaces contain
(`workspace/setup.py:35`) and what their recorded runs froze (`slime==0.3.1`).

## Provenance of the pins

`requirements.txt` was seeded from recorded artifacts, not written by hand.

For `verl` and `slime-rc0`, from the upstream images themselves:

```sh
docker run --rm --entrypoint python3 verlai/verl:vllm017.latest         -m pip freeze
docker run --rm --entrypoint python3 slimerl/slime:v0.5.0rc0-cu126      -m pip freeze
```

`pip freeze` already emits git URLs and commits for the custom-built packages
(`transformer_engine`, `apex`, `mbridge`, `torch_memory_saver`, `grouped_gemm`,
`cumem_allocator`, `nvdlfw_inspect`), so most of the closure is reproducible
verbatim. Four lines named a build-time local path instead and were rewritten to
the ref they were built from, recovered from the image's own git metadata:

| freeze line | rewritten to | recovered by |
|---|---|---|
| `deep_ep @ file:///sgl-workspace/DeepEP` | `git+https://github.com/deepseek-ai/DeepEP.git@b6ce310b` | `git -C /sgl-workspace/DeepEP log -1` in the image |
| `-e git+…/sglang.git@8ecf6b9d#egg=sglang&subdirectory=python` | non-editable `sglang[srt] @ git+…@8ecf6b9d#subdirectory=python` | nothing names `/sgl-workspace` by absolute path (checked across `tasks/`); the `[srt]` extra is ours and is required — see delta 12 |
| `-e git+…/Megatron-LM.git@48406695#egg=megatron_core` | moved to `sources.txt` | task scripts *do* name `/root/Megatron-LM` by absolute path |
| *(absent)* `--extra-index-url` | added per env | `torch==2.8.0+cu126` / `2.10.0+cu129` are local-version wheels, only on the PyTorch index |

Everything else is the upstream freeze, sorted by normalized package name.

### `slime-v0.3.1` comes from the runs, not from a `docker pull`

`slimerl/slime:latest` is a moving tag, so freezing it today would record
whatever was published today rather than what the four tasks actually ran on.
Each task carries its recorded run's `files/requirements.txt` — wandb's own
`pip freeze` of the process that produced the outcome — and that is the seed:
same artifact class as the image freeze above, and dated to the run instead of
to the pull.

Two cautions if you regenerate it. The wandb manifest is the *whole
interpreter*, so its tail is Ubuntu `dist-packages` (`command-not-found`,
`python-apt`, `ufw` …) that belong to the base image and not to the stack;
those lines are dropped. And it lists `slime==0.3.1` and `megatron-core`, both
of which are deliberately absent here — see "Neither slime nor verl is in its
own environment" below, and `sources.txt` for megatron.

The one pin that no freeze can supply is Megatron-LM's commit: it is installed
editable upstream, so the manifest records a version, not a ref — and the
version it records is `megatron-core==0.16.0rc0`, for which **no tag exists**
(`core_v0.16.0rc0` → 404 on the GitHub API). `sources.txt` therefore pins
`core_v0.16.0` (`3bec9aa9`), the release that rc0 became. That is a deliberate
approximation, not a transcription; if it ever matters, the exact commit is
still recoverable from an image:

```sh
docker run --rm --entrypoint git slimerl/slime:latest -C /root/Megatron-LM rev-parse HEAD
```

`torch_memory_saver` is the same class of pin. The wandb freeze records
`0.0.9.post1+slime`, which is not on PyPI: `slimerl/slime:latest` builds it
from `zhuzilin/torch_memory_saver@8d30c59`. Leaving it unpinned lets sglang's
`torch_memory_saver>=0.0.9.post1` resolve to PyPI 0.0.10, and pauseable CUDA
graphs then die with `Only hook_mode=preload supports pauseable CUDA Graph`.
The four slime-v0.3.1 tasks pin the git commit the image actually used.

### apex is in every slime closure, on purpose

`apex` is on neither PyPI nor in the upstream freeze as a version — it is built
from source in both images, and both `requirements.txt` files pin it by commit.
The two envs pin *different* commits, and only one of them is evidence-backed:
`slime-rc0` uses `@26bba57d`, which that image's own freeze names outright;
`slime-v0.3.1` still uses `@9e3568a6`, which is a guess. See delta 13.

It is not optional. `megatron.core`'s `ColumnParallelLinear` and
`RowParallelLinear` default to `gradient_accumulation_fusion=True` and raise at
**construction** if `fused_weight_gradient_mlp_cuda` cannot be imported — a hard
`RuntimeError` during model init, not a silent fallback. `slime_retool`'s
`prepare.sh` hits it before any training starts.

The trap is that apex installs perfectly happily without its extensions: no
`--cpp_ext --cuda_ext`, no error, just a pure-Python package missing the module
Megatron needs. `build-flags.txt` carries those flags, the Dockerfile smoke
imports the extension, and `docker/smoke.sh` actually calls
`wgrad_gemm_accum_fp32` — because an importable pure-Python shim would satisfy
the import and nothing else.

Passing `--no-gradient-accumulation-fusion` would also make the error go away,
and is the wrong fix: it changes the backward pass's accumulation dtype, and
this benchmark grades on reproducing curves recorded against images that had
apex compiled in.

### Binary CUDA wheels (`docker/wheels/`)

Two kinds of pin cannot be satisfied from an index on a cluster builder:
`torch` (and its `+cuXXX` siblings), which only the PyTorch index has, and
`flash_attn`, which PyPI ships as an sdist only. `docker/fetch-cuda-wheels.sh`
puts both on the host under `docker/wheels/<env>`, and each `env-*` stage in
`docker/Dockerfile` copies its own subdirectory in.

One subdirectory per environment, so that adding a `slime-v0.3.1` wheel does not
invalidate `verl`'s stage — but the filename tags below are still what keeps the
wheels apart, and they are not redundant with the split. `verl` and
`slime-v0.3.1` both pin `flash_attn==2.8.3`, built against torch 2.10 on CUDA 12
and torch 2.11 on CUDA 13 respectively. Two files, same version, not
interchangeable — installing the wrong one is an undefined symbol at best and a
segfault mid-run at worst. `docker/build-env.sh` reads both the `torch<X.Y>` and
the `cu<NNN>` tag out of the filename and refuses a wheel that disagrees with
this environment's own torch pin on either; a file dropped into the wrong
environment's directory is caught there rather than installed. The CUDA check
compares **majors** only, on purpose: `cu128` binaries run fine on a 12.9
prefix, which `verl`'s wheel relies on, while `libcudart.so.12` and
`libcudart.so.13` are different sonames and nothing bridges them.

`flash_attn` is the one to be careful with. Its extension links against torch's
C++ ABI, so a wheel is valid only for the exact torch it was compiled against —
and a stock build records nothing about that: the metadata version is a bare
`2.7.4.post1` whichever torch produced it. The filename is the only carrier, so
every `flash_attn` wheel here must be tagged `+cu<NNN>torch<X.Y>`, and
`fetch-cuda-wheels.sh` refuses a directory containing an untagged one.

That rule was bought the hard way. `slime-rc0`'s wheel used to be a
third-party prebuild whose filename said nothing; it had been built against a pre-2.8 torch,
and `import flash_attn` in the finished image died on `undefined symbol:
_ZN3c104cuda9SetDeviceEa` — the one-argument `c10::cuda::SetDevice` that torch
2.8 replaced with a two-argument one. It now comes out of `slimerl/slime`'s own
pip cache instead, repacked under `+cu126torch2.8`: the same binary slime's
recorded outcomes were produced with, and `sm_80`/`sm_90` only, which is the
arch list this image targets anyway. `verl`'s and `slime-v0.3.1`'s stay
third-party prebuilds (`mjun0812`, `+cu128torch2.10` and `+cu130torch2.11`):
upstream verl leaves no wheel behind to take, and `slime:latest` is a moving
tag whose pip cache is not a stable artifact to derive from. Both are 2.8.3,
which Dao-AILab does publish, so the prebuild is the same source compiled
against a different torch rather than an unrelated binary.

### Neither `slime` nor `verl` is in its own environment

This looks like an omission and is not. Verified in both images:

```
$ docker run --rm --entrypoint python3 slimerl/slime:v0.5.0rc0-cu126 -c 'import slime'
ModuleNotFoundError: No module named 'slime'
$ docker run --rm --entrypoint python3 verlai/verl:vllm017.latest -c 'import verl'
ModuleNotFoundError: No module named 'verl'
```

The upstream images are *runtime bases*: they carry the compiled dependency
stack, and the framework source arrives with the task. Each task's workspace
contains the checkout it was recorded against, and its launch scripts put it on
the path themselves —

```sh
export PYTHONPATH=/workspace:/root/Megatron-LM
```

— which is also why `/workspace` is first. Installing a framework version into
the environment would shadow the task's own copy with a different one, which is
the ground-truth-rewriting failure this registry exists to prevent. If a `slime`
or `verl` line ever appears in a `requirements.txt` here, it is a bug.

The four slime-v0.3.1 tasks' wandb manifests *do* list `slime==0.3.1`, which
looks like a counterexample and is not: that is the task's own workspace
checkout, which the recorded run pip-installed from `/workspace`. It is the
copy the task ships, not one the environment supplies, and it is dropped when
the manifest is turned into a `requirements.txt`. `collect_envs.py` enforces
this mechanically — a package whose name matches the environment's first
hyphen-separated segment is rejected.

## Known deltas from upstream

These are the "every difference explained" entries that gate G1; anything G1
turns up beyond them is a real finding.

1. **glibc.** All three environments are built on `ubuntu:22.04` (glibc 2.35).
   `verl` and the rc slime stack were already built on 22.04, so those are no
   delta at all. `slime:latest` is built on 24.04 (glibc 2.39), so
   `slime-v0.3.1` *is* a delta — but a one-directional one: nothing from that
   image is copied here. Every compiled package in this environment is either
   built from source against glibc 2.35 or installed from a `manylinux_2_28`
   wheel, both of which run on 2.35 and on 2.39. The delta would only bite if a
   future pin ships wheels tagged `manylinux_2_39` and nothing else; pip would
   reject those outright rather than install something subtly wrong.
2. **CUDA runtime lives in two places.** conda puts cudart and friends in
   `$PREFIX/lib`; the pip `nvidia-*` wheels put their own copies in
   `$PREFIX/lib/python3.12/site-packages/nvidia/*/lib`, and torch loads those.
   The upstream images have the same duplication (system `/usr/local/cuda` plus
   the pip wheels), so this mirrors them rather than diverging — but it is the
   first thing to suspect if G2 reports a symbol clash. Note the naming split:
   on `verl` and `slime-rc0` those wheels are `nvidia-*-cu12`, but NVIDIA
   dropped the suffix at CUDA 13, so `slime-v0.3.1`'s are bare
   (`nvidia-cublas`, `nvidia-cuda-runtime`, …) with only cudnn, cusparselt,
   nccl and nvshmem still carrying one, as `-cu13`. Grepping for `nvidia-*-cu12`
   alone will make that closure look like it has no CUDA runtime at all.
3. **`deep_ep` is omitted.** Upstream had a locally-built DeepEP in all three
   (`1.2.1+7febc6e` on `verl`, a git tree on `slime-rc0`, `1.1.0+6845ffd` in
   the slime-v0.3.1 runs). No task uses MoE, so the package is dropped rather
   than rebuilt from git.
4. **`flash_attn` carries a local version we added.** `+cu126torch2.8` on
   `slime-rc0`, `+cu128torch2.10` on `verl`, `+cu130torch2.11` on
   `slime-v0.3.1`, against upstream's bare `2.7.4.post1` and `2.8.3`. Same
   upstream version, same (slime-rc0), CUDA-matched (slime-v0.3.1) or
   ABI-compatible (verl, whose cu128 wheel runs on its 12.9 prefix) binary;
   the tag is ours, and it is there so the torch and CUDA major a wheel was
   built against are visible — see "Binary CUDA wheels" above.
5. **`transformer_engine` is the PyPI release, not upstream's git build.**
   Upstream slime-rc0 ships `2.5.0+af9467c` from
   `git+https://github.com/NVIDIA/TransformerEngine.git@af9467c` (the `v2.5`
   tag); upstream verl ships `2.12.0+5671fd3`; the slime-v0.3.1 runs froze
   `2.16.1`. We install the matching PyPI split (`transformer_engine` /
   `transformer_engine_cu12` or `_cu13` / `transformer_engine_torch`) at each of
   those versions, so the image build does not clone GitHub — `slime-v0.3.1`
   takes the `cu13` build of the same 2.16.1 release. Same version number, a
   different build of it. That cu13 wheel needs cuBLAS 13.3
   (`cublasLtGroupedMatrixLayoutInit_internal`); torch 2.11.0+cu130's
   `cuda-toolkit[cublas]==13.0.2` extra pins `nvidia-cublas==13.1.0.3`, so
   `slime-v0.3.1` records `nvidia-cublas==13.3.0.5` (the first 13.3 wheel)
   and `build-env.sh` re-applies it `--no-deps` after the source trees.
   `transformer_engine_torch` 2.5.0 is sdist-only on
   PyPI, so `slime-rc0` still compiles that one piece, but from the Tsinghua
   index rather than a git clone.
6. **`megatron-core` 0.16.0rc0 is pinned as the 0.16.0 tag.** `slime-v0.3.1`
   only; see "Provenance" above for why the exact ref is unrecoverable from a
   freeze.
7. **`slime-v0.3.1`'s and `slime-rc0`'s closures are curated, not verbatim.**
   `verl` pins every line of its upstream freeze. The two slime environments pin
   the packages that determine the stack — torch and its CUDA siblings, sglang,
   transformer_engine, transformers, flash_attn, ray, the build-time set — plus,
   on `slime-rc0`, sglang's own declared dependencies (see delta 12), and let pip
   resolve the rest. The recorded wandb manifest is the whole
   interpreter, several dozen lines of which are transitive leaves
   (`nvidia-cudnn-frontend`, `docstring_parser`, `wcwidth` …) that no task
   names and that no version choice here can affect. Pinning them would make
   the file look more rigorous without making the environment more reproducible,
   and would break the build the first time one of them yanked a release. The
   trade is real and is recorded here rather than hidden: these environments are
   reproducible at the level of the stack, not of every leaf. Concretely, on
   `slime-rc0` 115 packages differ in version from the upstream freeze; the ones
   that matter are pinned and the rest are leaves of leaves.
8. **`faiss-gpu` is not here at all.** The two search-r1 tasks need it and the
   other two must not have it, and this registry enforces equality across the
   tasks sharing an environment. It is installed by
   `tasks/slime_search_r1*/environment/prepare.sh` into `$PTDBENCH_PREPARED`
   instead — see the comment there for why `--target` and not a plain
   `pip install`.
9. **`nvidia-cuda-crt` is pinned to 13.0.88 on `slime-v0.3.1`.** It is not a
   stack package the tasks name — it arrives as an unversioned dependency of
   `nvidia-cuda-nvcc`, itself pulled by sglang → flashinfer → cuda-tile at
   `>=13.2,<13.3`. Left free it resolved to 13.4.92, whose `host_runtime.h`
   defines `__cudaLaunch` as one argument while conda nvcc 13.0.88 still emits
   two-argument stubs, so apex's `--cuda_ext` compile failed. 13.0.88 is the
   CRT that matches this environment's nvcc, not the wandb freeze (13.3.73).
   `nvidia-cuda-nvcc` itself cannot be pinned to 13.0: flashinfer requires 13.2.
10. **Megatron-LM is patched, not vanilla, on `slime-v0.3.1`.** One hunk, in
   `megatron/core/inference/contexts/dynamic_context.py`, from
   `patches/Megatron-LM/0001-tms-hook-mode.patch`. It is *not* a delta from
   upstream — it is what removes one: `slimerl/slime:latest` applies the same
   change from its own `docker/patch/latest/megatron.patch`, so a vanilla clone
   at the pinned commit is what diverges from the image we reproduce. Without
   it the SGLang rollout engines die at CUDA-graph capture on
   `AssertionError: Only hook_mode=preload supports pauseable CUDA Graph`,
   because importing Megatron flips a process-global in torch_memory_saver.
   The patch file carries the full reasoning. Note the asymmetry: we take one
   hunk, slime's patch has 21 — the rest target Megatron's own training and
   inference paths, which nothing here exercises. Any further divergence from
   `slime:latest` that traces to an unapplied hunk belongs in this list, or in
   a second patch file.
11. **Megatron-LM is patched, not vanilla, on `slime-rc0` too.** Three patches,
   touching four files. Like delta 10 these *remove* a divergence rather than
   create one: the Megatron working tree inside
   `slimerl/slime:v0.5.0rc0-cu126` carries 9 modified files on top of the
   commit in `sources.txt`, so a clean clone at that commit is what differs
   from the image whose outcomes we reproduce. Recover the full set with

   ```sh
   docker run --rm --entrypoint bash slimerl/slime:v0.5.0rc0-cu126 \
       -lc 'git -C /root/Megatron-LM diff'
   ```

   We take three of the nine, each for a reason written in the patch file:
   `0001` restores `megatron.core.distributed.custom_fsdp`, which mbridge
   imports at module scope and which the HF → torch_dist conversion in every
   `rlve_hyper` `prepare.sh` therefore needs; `0002` restores
   `mpu.destroy_process_groups` / `reload_process_groups`, which slime calls
   behind `hasattr` on every offload transition, so an unpatched tree makes
   them silent no-ops and holds NCCL buffers through each rollout; `0003` tags
   TE parameters with `parallel_mode`, which slime reads when deciding whether
   a weight is sharded before shipping it to the rollout engine.

   The other six are left out: one is a Megatron-internal MTP fix for a model
   class these tasks do not use (`gpt_model.py`), and five implement the
   `post_self_attn_layernorm` / `post_mlp_layernorm` feature, which only slime's
   glm4 and glm4moe paths ever enable. Both groups are self-consistent, so
   dropping them changes nothing for Qwen2.5. If a glm or MTP task is ever added
   to this environment, those five files are the first thing to re-apply.
   `0002` is the one to be careful with: its two files are a single change, and
   applying either alone is worse than applying neither — the patch header
   explains why.
12. **sglang is installed from git with its `[srt]` extra, and its declared
   dependencies are pinned to the upstream freeze.** `slime-rc0` only. Three
   things, all on one line of the closure:

   ```
   sglang[srt] @ git+https://github.com/sgl-project/sglang.git@8ecf6b9d…#subdirectory=python
   ```

   *The extra* is not cosmetic. `sglang==0.5.0rc0` with no extra installs the
   package and none of the serving runtime — uvloop, fastapi, uvicorn, xgrammar,
   flashinfer and sgl-kernel all live under `runtime_common`/`srt`. It imports
   cleanly, so nothing complains until slime reaches for the engine in
   `slime/backends/sglang_utils/sglang_engine.py:7`, inside a Ray actor about
   ten minutes into a run: `ModuleNotFoundError: No module named 'uvloop'`.
   Upstream needs no extra because it installs editable into an image that
   already has the runtime.

   *The git ref* rather than PyPI: the 0.5.0rc0 sdist on PyPI pins
   `sgl-kernel==0.3.2`, while the tree at this commit pins 0.3.3 — and 0.3.3 is
   what the upstream image froze. Same version number, a different kernel.

   *The leaf pins*: sglang's own declared dependencies (base + `runtime_common`
   + `srt`) are pinned at the versions the upstream image froze — `uvloop`,
   `scipy`, `pynvml`, `nvidia-ml-py`, `cuda-python`, `msgspec`, `tiktoken`,
   `modelscope` and ~20 more. They are not stack packages and no task names
   them; left free, pip resolves today's releases instead of August 2025's, and
   at least one of those (`pynvml` 12 → 13) is an API break. Every version is
   one that demonstrably coexisted in the upstream image with this same
   sglang/torch/ray/transformers. The rule is bounded on purpose — sglang's
   direct dependencies, not their transitive closure; see delta 7.

   One package was *dropped* to make this resolve: `openai-agents==0.2.9`, which
   requires `openai>=1.99.6` while sglang's `runtime_common` pins
   `openai==1.99.1` exactly. It has no claim to be here — it is in neither the
   upstream freeze nor the slime checkout's `workspace/requirements.txt`, and
   nothing under `tasks/rlve_hyper/` imports `agents`. It arrived because this
   closure was seeded from `slime-v0.3.1`, which does pin it (0.0.7) because the
   recorded wandb manifests there list it. Dropping it removes a delta rather
   than adding one.
13. **apex is pinned to `@26bba57d` on `slime-rc0`, not `@9e3568a6`.** The old
   pin came from the `slime-v0.3.1` seed, where it carries no comment at all;
   the rationale was written here, on the `rlve_hyper` copies — *"Commit is the
   last one before `slimerl/slime:v0.5.0rc0-cu126` was published."* That was
   unnecessary and impossible in one move. Unnecessary because that image's own
   freeze names the ref outright — apex is one of the lines you get from

   ```sh
   docker run --rm --entrypoint python3 slimerl/slime:v0.5.0rc0-cu126 -m pip freeze
   ```

   and impossible because `9e3568a6` is dated 2026-08-04, roughly a year *after*
   that image was built; `26bba57d` is dated 2025-08-21. Both dates are
   recoverable offline from the mirror this repo already keeps:

   ```sh
   git -C docker/gitmirror/_store/github.com-NVIDIA-apex.git log -1 --date=iso \
       --format='%ad %s' <commit>
   ```

   The bump is not cosmetic, which is why it was verified by building rather
   than by reading: `26bba57d` is titled *"Remove version dependent macros &
   extension specific arch flags except fmha"*, i.e. it changes exactly the
   machinery that decides which SM architectures the extensions compile for.
   It was rebuilt with `--cpp_ext --cuda_ext` under this image's
   `TORCH_CUDA_ARCH_LIST=8.0;9.0`, exercised with the same
   `wgrad_gemm_accum_fp32` call `docker/smoke.sh` makes (on an A800, so sm_80
   ran for real), and then checked with `cuobjdump --list-elf`: every CUDA
   extension it produces — `fused_weight_gradient_mlp_cuda`, `amp_C`,
   `fused_layer_norm_cuda`, `scaled_upper_triang_masked_softmax_cuda` — carries
   both `sm_80` and `sm_90`. That last step is the one the commit title asks
   for, and it is now a check in `docker/smoke.sh` rather than a thing someone
   did once: the wgrad probe alone cannot catch it, because an apex compiled for
   the wrong architecture still imports and still passes on whichever card the
   smoke host happens to have.

   `slime-v0.3.1` is deliberately **left on `9e3568a6`**. The same argument does
   not transfer: that environment is reconstructed from recorded wandb manifests
   rather than from a pullable image (see "Provenance"), so there is no freeze
   to read the true ref out of, and changing a compiled package under four
   already-graded tasks on the strength of an analogy is not an improvement. The
   guess is still a guess there, and now it is a *labelled* guess — that is the
   whole of the change on that side.
14. **`sglang-router` is pinned to 0.1.9 on `slime-rc0`, not 0.3.2.** 0.1.9 is
   what the upstream image froze. 0.3.2 came from the `slime-v0.3.1` seed and
   survived unnoticed for a structural reason worth naming: sglang does not
   declare a dependency on `sglang-router` at all (`importlib.metadata.requires`
   returns nothing for it), so pip never had cause to object, and no import-time
   check would have either. It was an undocumented two-minor-version delta that
   only a diff against the freeze could find.

   slime drives the router through a narrow, entirely private surface, and every
   part of it was exercised against 0.1.9 in a container before the pin moved:

   | call site | what it uses |
   | --- | --- |
   | `slime/ray/rollout.py:129` | `RouterArgs(host=, port=, balance_abs_threshold=, prometheus_port=)`, plus `log_level` and `request_timeout_secs` behind `hasattr` |
   | `slime/backends/sglang_utils/sglang_engine.py:127` | `POST /add_worker?url=` |
   | `slime/backends/sglang_utils/sglang_engine.py:191` | `POST /remove_worker?url=` |
   | `slime/rollout/sglang_rollout.py:210` | `GET /list_workers` |

   All four kwargs are accepted, both `hasattr`-guarded attributes exist, and
   all three endpoints returned 200 against a stub worker. The two guarded
   attributes are the reason this needed executing rather than reading: on a
   version where they are absent, slime does not fail — it silently runs the
   router at its default log level and default timeout.

## Patching a source tree

`build-env.sh` applies `docker/envs/<env>/patches/<dir-name>/*.patch`, in
sorted order, between `git checkout --detach <commit>` and `pip install -e`.
`<dir-name>` matches the first column of `sources.txt`. No directory means no
patches; an empty directory is an error rather than a no-op, so a removed patch
cannot go unnoticed.

Generate patch bodies with `git diff` inside a clone at the pinned commit, never
by hand — a plain `git apply` is tried first and the `--3way` fallback needs the
real blob ids from the `index` line. A patch that no longer applies fails the
build, which is the intent: it means the pin moved out from under the patch and
someone has to look. The tree is deliberately left dirty afterwards, so
`git -C /opt/conda/envs/<env>/src/<dir> diff` inside a built image answers "how
does this differ from the pin" honestly.

Prefer a patch here over editing `tasks/*/workspace/` when the thing being fixed
is a property of the *environment* rather than of a task's code — and check what
the upstream image does first. Several problems that look like they need a slime
source change are already solved by a patch in `slimerl/slime:latest`.

## Why not merge requirements across tasks

Taking the union of two tasks' requirements would mean adding a task can change
an existing task's environment. For a benchmark that grades by reproducing a
specific training failure, that silently rewrites ground truth. So the rule is
equality, and the remedy for a task that genuinely needs something different is
a new environment name, not a bigger shared one.

A task needing one or two extra *pure-Python* packages should not fork an
environment either — that is what `environment/prepare.sh` is for.
